# ЗНАЙДЕНО — release readiness audit

Дата перевірки: 2026-10-27  
Гілка: `pre-release/1.0.0-hardening`  
Production service: Render `srv-dbcbps3rjlhs73bfunog`

## Рішення

**NO-GO для повноцінного комерційного релізу з прийманням реальних платежів**, доки не пройдено перелічені нижче обов'язкові перевірки. Технічний реліз для обмеженого тестування можливий лише з вимкненими платежами, підтвердженим деплоєм і перевіркою доступу до даних.

## Виявлено та виправлено в коді цієї гілки

- Telegram webhook тепер перевіряє заголовок `X-Telegram-Bot-Api-Secret-Token` у constant-time і відхиляє запити без правильного секрету.
- Реєстрація webhook передає `secret_token` та обмежує типи оновлень потрібними повідомленнями й pre-checkout.
- Вимкнено заголовок `X-Powered-By`.
- Додано базові HTTP security headers: `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`, `Permissions-Policy` та HSTS для HTTPS.
- CORS більше не відкритий для довільних браузерних origin: дозволено `SERVER_URL` та явні origin із `ALLOWED_ORIGINS`.
- Обмежено JSON body до 100 KB.
- Кнопку Telegram Stars у Mini App зроблено компактною. Вона залишається вимкненою, доки платіжна конфігурація не ввімкнена сервером.

## Критичні перевірки перед комерційним запуском

1. **Render deploy:** перевірити, що найновіший commit має статус `live`, а не `queued/build_in_progress/update_failed`. Перевірити `GET /health` та реальний запуск `/start` у Telegram.
2. **Webhook secret:** додати стабільний секрет `TELEGRAM_WEBHOOK_SECRET` у Render Environment (32+ випадкових символів із допустимих Telegram символів) та перевірити, що webhook успішно зареєстрований. Якщо змінюється секрет — переконатися, що Telegram webhook оновлено.
3. **Production bypass:** перевірити, що `ENABLE_TEST_PREMIUM_BYPASS` відсутній або не дорівнює `true`.
4. **Payments:** поки не пройдено тестову оплату Stars, перевірку повторної доставки update, помилок БД, повернення та стану підписки, залишити `PAYMENTS_ENABLED=false`. Перевірити `TELEGRAM_STARS_PREMIUM_PRICE`, міграції `star_payments` та реальну активацію/скасування підписки.
5. **Database:** перевірити в Supabase, що застосовані всі потрібні міграції; RLS увімкнено на персональних таблицях; `anon` та `authenticated` не мають доступу до службових платіжних таблиць; service-role key зберігається тільки на сервері.
6. **Legal identity:** заповнити фактичний статус постачальника (ФОП/юридична особа/інша законна модель), офіційні реквізити та адресу для юридичних звернень. Не вигадувати статус або адресу.
7. **Privacy:** звірити фактичний список даних, постачальників, регіони обробки, строки зберігання, порядок видалення й правові підстави. Опублікувати лише після підтвердження власником.
8. **Consumer/payment terms:** оприлюднити ціну, період доступу, функції, порядок поновлення/скасування, звернень і повернення; отримати юридичну перевірку українського права.
9. **Telegram rules:** цифрові функції, що продаються всередині Telegram, оплачуються Telegram Stars. Не приховувати альтернативний платіжний спосіб і не використовувати картковий checkout усередині Mini App для обходу вимог Telegram.
10. **Backups/incident response:** перевірити резервне копіювання бази, доступ до журналів, процедуру відкликання токена бота та ротації секретів.

## Поточні спостереження з коду

- Вебхук раніше приймав запити без Telegram secret header. Це дозволяло підробляти вхідні update; перевірку додано, але її потрібно підтвердити після production deploy.
- У `server.js` існують API legal endpoints із дуже коротким текстом, який не відповідає повним текстам у Mini App. Їх потрібно узгодити до публічного релізу, щоб користувач не отримував різні версії умов залежно від точки входу.
- Повні юридичні тексти в `index.html` прямо позначені як тестова редакція та повідомляють, що перед комерційним запуском потрібні перевірка й реквізити. Не прибирати ці попередження до фактичного завершення перевірок.
- `server.js` має кілька API catch-блоків, які повертають `err.message` клієнту. Перед масштабним публічним запуском замінити їх на загальні повідомлення, залишаючи технічні деталі лише в серверних логах.
- Наявність коду міграцій у GitHub не доводить, що ці міграції виконані в production Supabase.
- Наявність автоматичних тестів не доводить, що реальні платежі, вебхук і production secrets перевірені end-to-end.

## Smoke test за 10–15 хвилин

- [ ] `GET /health` повертає `ok: true`.
- [ ] Невалідний або відсутній `x-telegram-init-data` отримує 401.
- [ ] Звичайний користувач не має доступу до `/api/admin/*`.
- [ ] POST на `/telegram-webhook` без правильного secret header отримує 401.
- [ ] `/start` показує актуальне привітання; Mini App відкривається.
- [ ] Новий користувач отримує 4-денний trial, потім — free tier згідно з серверною політикою.
- [ ] Один користувач не може прочитати/видалити фільтри іншого.
- [ ] При `PAYMENTS_ENABLED=false` рахунок не створюється і Premium не активується.
- [ ] Legal docs відкриваються й містять однакові умови в усіх точках входу.
- [ ] Після перевірок немає нових 5xx у Render logs.

## Платежі карткою

Кандидати для окремого веб-checkout після реєстрації/верифікації мерчанта: Fondy, WayForPay, LiqPay. Підключення потребує укладення договору, merchant credentials, перевірки webhook-підпису, idempotency, повернень і фіскальних/податкових вимог. Не вмикати картковий checkout для цифрової підписки всередині Telegram Mini App без перевірки відповідності правилам Telegram.
