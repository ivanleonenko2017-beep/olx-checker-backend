# Знайдено 1.0.0 — план м'якого запуску

## Перед запрошенням користувачів

1. Власник проходить Telegram test plan з релізного звіту.
2. У /status перевіряє RSS, heapUsed, uptime, webhook та останній цикл worker.
3. Перевіряє, що /testnotify надсилає повідомлення лише йому, з поміткою «ТЕСТ».
4. Переконується, що платежі не використовуються під час технічного тесту.
5. Фіксує поточний Live deploy ID і commit перед запрошенням першого тестувальника.

## План 5–20 довірених користувачів

- Етап 1: запросити 5 людей, які погодилися на тест.
- Перші 24 години: не додавати нових користувачів, перевіряти Render Events/logs, /status, memory та помилки Supabase.
- Якщо немає блокерів, додати ще до 5 користувачів.
- Наступні 24–48 годин: перевірити пошук, дублікати, затримки webhook, роботу після простою та звернення користувачів.
- Лише після стабільного періоду можна розширити групу до 20 довірених користувачів.
- Не робити публічну рекламу та не приймати реальні платежі до юридичної, платіжної та backup-перевірки.

## Що дивитися протягом 24–72 годин

- Render deploy: статус Live, commit збігається з production branch.
- Render Events: немає нових server_failed/restarts.
- Application logs: немає heap out of memory, uncaught exception, Supabase failures.
- HTTP logs: немає серії 5xx; 4xx розбирати за маршрутом та причиною.
- Memory: RSS нижче 410 MiB; перевіряти тенденцію, а не один семпл. HeapUsed дивитися в /status.
- Worker: останній успішний цикл оновлюється, фільтри не зависають.
- Telegram webhook: немає накопичення pending updates; тестове повідомлення приходить адміністратору.
- Пошук: міста, моделі, пам'ять та стан відповідають запиту; аксесуари не потрапляють у телефонну видачу.
- Supabase: немає нових помилок; кількість users/filters не зменшується несподівано.

## Критерії негайної зупинки тесту

Зупинити запрошення нових користувачів і розібратися, якщо є хоча б один пункт:

- RSS досягає 410 MiB або зростає без стабілізації.
- Новий heap out of memory, server_failed або повторні рестарти.
- Повторні/подвійні сповіщення, чужі оголошення або порушення фільтрів.
- Масові 5xx, збої Supabase чи накопичення webhook queue.
- Витік чужих даних, доступ до адмінки неадміністратором або некоректний Premium.
- Платіжний статус/тариф змінюється без підтвердженого платежу.

## Відкат Render

1. Відкрити Render Dashboard → сервіс `srv-dbcbps3rjlhs73bfunog` → Deploys.
2. Знайти останній відомий здоровий deploy і звірити commit.
3. Запустити Rollback на нього через Dashboard; не переписувати Git history.
4. Дочекатися Live та перевірити startup logs, Supabase connection і webhook.
5. Повторити /status та контрольний Telegram smoke test.

Точка, зафіксована 25.11.2026: deploy `dep-dc3e950jo6nc73elfo00`, commit `f8339d3495746c2732b014bb9a5e3bc8ea4bc255`. Перед фактичним відкатом завжди перевірити поточний Render status.

## Як зупинити фонові перевірки

У Render вже підтримується `ENABLE_BACKGROUND_WORKER=false`. Це вимикає background worker після restart/redeploy, але не вимикає webhook чи API. Використовувати лише як аварійний крок власника; після виправлення повернути поточне значення.

## Як зупинити нові реєстрації

Окремого перевіреного registration kill switch у поточному коді немає. Не додавати випадкову env-змінну й не вважати, що вона працює. Повне тимчасове призупинення Render зупинить також Mini App API та Telegram webhook; це аварійний захід, а не штатний спосіб обмежити реєстрацію.

## Обмеження інфраструктури

Render Free може засинати після простою; перший запит може мати затримку. У поточному проході не змінювали тариф, environment variables чи кількість інстансів. Backup/PITR Supabase потрібно перевірити власнику в Dashboard. Production Vercel URL окремо не підтверджено.
